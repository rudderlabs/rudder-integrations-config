# Edit an existing definition

Read [`CONVENTIONS.md`](../../../CONVENTIONS.md) first — its rules apply to every new or changed
field. This skill covers what goes wrong when the definition **already has saved configs**.

## 1. Find the file that owns the change

| Change                                                       | Owner                                                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| What renders, labels, per-field visibility (`preRequisites`) | `ui-config.json` — never `db-config.json`                                                  |
| Which persisted values are valid                             | `schema.json`                                                                              |
| Which keys persist / reach device mode                       | `db-config.json` `destConfig` / `includeKeys`                                              |
| Catalog visibility, beta badge, icon                         | `db-config.json` `options` (accounts: `displayOptions`)                                    |
| `ga4_v2` UI                                                  | `ui-config.jt` + `ui-default.json`; `ui-config.json` is generated by `npm run pre-process` |

A select's options and the schema `enum`/`default` are one change — editing one side publishes an
option the backend rejects, or the reverse.

Runtime behaviour (endpoint switching, rejecting a legacy auth value, SSRF/egress checks, SDK
behaviour) lives in rudder-transformer or the SDKs, not here. Device-mode exposure for a new
platform also needs the SDK integration to exist; metadata alone does not ship it.

## 2. Keep saved configs valid

Every edit is checked against configs customers already saved. Before tightening anything, ask
"what does an existing config that never had this key, or has the old value, do now?"

- **`default` is written into configs, not just shown.** The validator runs AJV with
  `useDefaults: true` (`src/validator/index.ts`), so a schema `default` is injected into any config
  that omits the key. Flipping a default silently changes every saved config that omitted it, and an
  injected default does **not** satisfy `required` inside an `if`. Migrate existing configs to an
  explicit value first; flip the default only after the migration is verified.
- **A new key is optional at the top level.** Enforce it only in the conditional branch that needs
  it (`allOf`/`if`/`then`), and keep the UI field `required: false` so the generator does not push
  it into top-level `required`. When a conditional is keyed on a discriminator, put
  `required: ["<discriminator>"]` **inside the `if`** — otherwise a config missing the
  discriminator matches the `if` and is routed into the new branch.
- **Removing an option from the UI is not removing it from the schema.** If saved configs carry the
  value, keep it in the schema `enum`/conditionals (and `db-config.json` metadata) so they still
  render and save. The generator will recommend deleting it — that diff is intentional; don't apply
  it.
- **Don't narrow an existing `regex`/`pattern` as a side effect.** Saved values may be `{{ }}`
  templates or `env.` references. Tightening is its own reviewed change; CONVENTIONS' plain-pattern
  rule is for new fields.
- **Moving a key between `defaultConfig` and a source type is breaking** —
  [CONVENTIONS.md](../../../CONVENTIONS.md#both-files-must-agree-and-moving-a-field-later-is-breaking).
- When requirements are unresolved, keep current validation and defaults; don't add a stricter rule
  "to be safe". Don't invent a visible field for an orphan schema key, or renderer metadata
  (e.g. a "deprecated option" flag) the webapp has not been verified to read.

## 3. Visibility gates and GA

`options.hidden` (accounts: `displayOptions.hidden`) is `true`/`false` or
`{ "gate": { "flags": [{ "name", "value" }], "condition" } }`. The gate **hides when the flags
match**: `{ "name": "AMP_enable-<thing>", "value": false }` hides until the flag is on. Each flag
needs both `name` and boolean `value`; two or more flags need `condition` (`and`/`or`). The legacy
`featureFlagName`/`featureFlagValue` object is rejected.

- The gate is enforced twice: the webapp hides the definition, and config-backend rejects CREATE
  with a 403 (update is not gated). Removing it from the definition unblocks both; no backend change.
- **GA = delete `options.hidden` and `options.isBeta`.** Omit `isBeta`, never set it `false`.
  `options` must stay non-empty — `icon` keeps it so. On deploy the whole definition is re-sent, so
  deleted nested keys are dropped from the stored definition.
- **One flag can gate several definitions and products.** GA one definition by removing its gate —
  never flip the shared flag. A source and its account definition gated together use the same flag
  name in both places.
- Flag names follow `AMP_enable-<thing>`. This repo cannot provision flags or billing features;
  don't invent billing feature names, and leave flag provisioning to the rollout owner.
- **Option vs field gating:** `featureFlag` on a `singleSelect` option hides that option (both
  builders support it); `preRequisites.featureFlags` hides the whole field. Don't use one for the
  other.
- `options` and `config` are both `additionalProperties: false` in
  `src/schemas/destinations/db-config-schema.json`: a new key needs its schema property first. Read
  that file's `allOf` before combining flags — `supportsVisualMapperV2: true` excludes the legacy
  VDM/audience flags.

## 4. The schema-generator gate

```bash
npm run check:schema:destination <dir>     # or check:schema:source <dir>
```

- CI pipes changed files to `scripts/run-schema-validation.sh`, which fails on **any** line
  containing "warning" (recommendations, such as top-level `additionalProperties: false`, are
  printed but not fatal). It validates only the first changed definition — check every one you
  touch locally.
- **Pre-existing warnings on a definition you touch become yours.** The usual inherited one is a
  missing `items.required: ["provider"]` under `consentManagement.<source>`. Align the schema with
  the generator, and say in the PR which changes were inherited and which are your scoped change.
- **Silence proves nothing for a typo'd name** (exit 0 either way) **or for `EXCLUDED_DEST`** (`scripts/schemaGenerator.py`: postgres, bq,
  azure_synapse, clickhouse, deltalake, kafka) — they are skipped and exit 0. Validate them with
  fixtures.
- The generator does not walk `redirectGroups` or `sdkTemplate.groups`; those schema entries are
  hand-maintained, and `update:schema:*:force` deletes them. A `regex` on `textInput` and
  `dynamicDataSelect` becomes the schema `pattern` — keep the regex in `ui-config.json` as the
  source of truth.
- If the generator crashes (e.g. `KeyError` on a source field using destination-style
  `preRequisites`), that is a tooling bug — report it; don't treat it as a clean diff.
- Never add a per-definition branch or exemption to a shared script to get one change through
  ([CLAUDE.md](../../../CLAUDE.md#shared-scripts-are-repo-wide-contracts)). The exception runs the other way: if the generator drops a constraint the UI enforces, fix
  the generator branch (with generator tests) rather than accepting the weaker schema.

## 5. Tests

- Behaviour changes go in the definition's fixture — `test/data/validation/{destinations,sources,accounts}/<dir>.json`.
  **Add a new case; don't edit an existing one.** Fixtures for an omitted key must reflect the
  current default; legacy compatibility cases set the old value explicitly.
- Keep `test/validation.test.ts` for framework-level and parameterised cross-definition checks — no
  one-off assertions for one destination (registering it in a shared parameterised list such as
  `warehouseDestinationNames` is fine). Name what a test checks; no ticket or plan ids in titles.
- A cross-key `db-config.json` rule JSON Schema cannot express goes in `src/validator/index.ts`, with
  positive and negative cases in `test/validator/validator.test.ts`.
- `test/consentManagementFieldsIntegrity.test.ts` requires `consentManagement` for every
  supported source type; when it fails it throws on `undefined.includes`. Fix coverage there — don't
  add or drop a source type to satisfy it.
- An `err` string must match AJV output exactly.

## 6. Local traps

- **Worktree:** run `npm ci --ignore-scripts` inside it (a symlinked `node_modules` fails with
  `Cannot find module 'ajv-keywords'`), then `npx husky install` or `git commit` fails in the
  hook. Never `--no-verify`.
- **A scoped Jest run exits non-zero with every test passing** — `jest.config.js` enforces 100%
  global coverage. Judge by the `Tests:` line. A run that times out is a failure: rerun with
  `--testTimeout=120000 --maxWorkers=2`.
- `npm run format` then `git diff --exit-code` is what CI checks (markdown included). Any Python file
  anywhere — including skill helper scripts — must be Black-formatted.
- Commits are Conventional; commitlint checks the latest commit, so reword auto-generated commits
  (e.g. Copilot Autofix) before pushing.
- Never run `scripts/deployToDB.py` / `deployAccountsToDB.py` with `--no-dry-run` locally. Verbose deploy logging writes request
  bodies and the basic-auth credential to `deploy-debug.log` in cleartext.
- Don't commit e2e screenshots, recordings or run reports.

## Verify

```bash
npm run check:schema:destination <dir>     # zero warnings for every definition touched
npx jest test/validation.test.ts
python3 scripts/validate_account_definitions.py <dir>   # if db-config.json or accounts/** changed
npm run format && git diff --exit-code
```
